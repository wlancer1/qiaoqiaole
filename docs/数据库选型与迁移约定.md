# 数据库选型与迁移约定

## 当前方案

项目当前使用 `sql.js + SQLite`：

- SQLite 数据库在 Node.js 进程中运行；
- 数据库默认保存到 `/tmp/qiaoqiaole.sqlite`；
- 正式运行时应通过 `SQLITE_PATH` 配置到持久化目录，例如 `/data/qiaoqiaole.sqlite`；
- 变更后通过 SQLite 文件持久化，部署时必须配置持久化磁盘或可靠备份。

## 后续方案

当用户量、并发写入或部署规模增长后，再迁移到 PostgreSQL。4GB 内存服务器也可以运行 PostgreSQL，但当前阶段不为了数据库升级增加部署复杂度。

## 迁移兼容约定

新增数据库功能时遵循以下规则，确保以后可以平滑迁移：

- 优先使用标准 SQL，不依赖 SQLite 特有语法或宽松类型转换；
- 主键继续使用应用层生成的 UUID 字符串，避免迁移时重建关联关系；
- 时间字段统一使用 ISO 8601 格式保存，迁移 PostgreSQL 时再转换为 `timestamptz`；
- 用户、仓库、库存、出入库记录和作品之间继续使用明确的外键关系；
- 画布内容、作品快照等半结构化数据使用 JSON 结构保存，未来迁移到 PostgreSQL 时使用 `jsonb`；
- 数据库访问逻辑集中在 API 层，不让前端直接依赖 SQLite 文件；
- 不把 SQLite 文件路径、SQLite 特有函数或 SQL 方言写死到业务组件中。

## 当前核心表

- `users`：用户账号
- `sessions`：登录会话
- `warehouses`：豆子仓库
- `inventory`：仓库库存
- `inventory_transactions`：出入库流水
- `projects`：我的作品和最近项目
- `project_likes`：社区作品点赞记录，使用 `(project_id, user_id)` 唯一约束防止重复点赞
- `project_comments`：社区作品评论记录

`projects` 的 `shared_to_community`、`shared_at` 和 `likes_count` 字段用于标记社区分享状态和热门排序。社区数据仍由 API 层访问，不让前端直接读取 SQLite 文件。

## 迁移时的目标

迁移到 PostgreSQL 时，需要准备独立迁移脚本，完成以下内容：

1. 创建 PostgreSQL 表结构和索引；
2. 导出并转换 SQLite 中的用户、仓库、库存、流水和作品数据；
3. 校验外键关系、库存合计和作品数量；
4. 为画布快照、图片元数据等新字段补充 `jsonb` 结构；
5. 切换 `DATABASE_URL` 或 PostgreSQL 连接配置，并保留 SQLite 备份作为回滚依据。
