# 拼豆库存检测与“开始拼豆”会话设计

状态：已确认，可用于生成 Codex Goal 实施计划  
日期：2026-08-08  
项目：巧巧乐 H5  
参考界面：`6121786192676_.pic.jpg`

## 1. 背景

现有产品已经具备图纸编辑、豆子清单、MARD 221 色号映射、豆子仓库和库存出入库能力，但“图纸需要多少豆子”“仓库是否足够”“实际拼到哪里”仍是互相分离的流程。

本设计把以下能力串成一条完整路径：

1. 从豆子清单检测当前仓库库存。
2. 明确展示充足色号、缺豆色号和缺少数量。
3. 即使库存不足也允许开始拼豆。
4. 进入以色号为完成单位的“开始拼豆”页面。
5. 自动保存进度并支持中途退出、跨次继续。
6. 整件完成后由用户决定是否扣减库存。
7. 从编辑器保存弹窗和“我的作品”操作弹窗进入同一套拼豆会话。

## 2. 已确认的产品决策

- 拼豆进度以“完成色号”为单位，不以逐颗豆子为单位。
- 库存不足只提示，不阻止开始拼豆。
- 开始拼豆时不预扣库存。
- 完成单个色号时不扣库存。
- 中途退出保存进度，不扣库存。
- 完成整件作品后，用户可以选择“完成并扣减库存”或“完成但不扣减库存”。
- 扣减前重新检测库存；任何色号不足时不允许部分扣减，也不允许负库存。
- “开始拼豆”页面采用“色号优先、画布为主”的结构，UI 层级接近参考图。
- 编辑器保存弹窗增加“保存并开始拼豆”。
- “我的作品”点击作品图片后打开操作弹窗，包含开始/继续拼豆、编辑、分享和删除等操作。
- 完成结果一旦确认即不可改写：“完成但不扣减”之后不能再通过该会话补扣库存，需要用户在仓库中手动出库。
- 会话创建时保存不可变的图纸网格与每色需求快照；拼豆渲染、检测基准和最终扣减都使用该快照。
- 首版采用服务端进度优先，不做多设备自动合并。

## 3. 目标与非目标

### 3.1 目标

- 用户能在开始前判断现有库存能否完成作品。
- 用户能快速定位并逐色完成图纸。
- 关闭页面或中途退出后可以恢复到上次进度。
- 库存扣减具备明确确认、原子性和幂等性。
- 同一作品的所有入口进入同一个未完成拼豆会话。
- 页面适合 H5 单手操作，并复用现有画布、豆子清单和仓库能力。

### 3.2 首版非目标

- 不记录每一颗豆子的独立完成状态。
- 不在开始时预占或扣减库存。
- 不允许库存扣成负数。
- 不做多人协作拼豆。
- 不做复杂工时分析、排行榜或成就系统。
- 不自动推断用户现实中未录入仓库的豆子数量。
- 不在图纸发生结构变化后自动迁移旧拼豆进度。

## 4. 统一用户流程

### 4.1 从豆子清单进入

豆子清单底部增加两个操作：

- `检测豆子库存`
- `开始拼豆`

流程：

`豆子清单 → 选择仓库 → 检测库存 → 查看检测结果 → 以检测返回的作品版本创建/恢复会话 → 会话级复核 → 开始/继续拼豆`

项目级检测结果必须返回 `projectRevision`。后续创建会话携带 `expectedProjectRevision`；检测后项目若被修改，创建失败并要求重新检测，不能静默按新版本开始。

如果当前内容尚未保存为用户作品：

- 编辑器或分步生成预览：先打开保存弹窗。
- 社区模板或他人作品：先创建一份归属于当前用户的作品副本，再进入库存检测和拼豆会话。

如果用户未登录：

- 普通豆子清单仍可查看。
- 点击库存检测或开始拼豆时要求登录。
- 登录成功后恢复原操作，不要求用户重新寻找入口。

### 4.2 从编辑器保存弹窗进入

保存弹窗提供：

1. `保存并开始拼豆`：主按钮。
2. `仅保存作品`：次按钮。
3. `取消`。

执行顺序：

`提交保存 → 服务端确认保存成功并返回结构版本 → 查询已有拼豆会话 → 比较结构版本 → 创建/恢复会话 → 按会话快照检测库存 → 开始或恢复会话`

规则：

- 保存失败时停留在弹窗中，不进入拼豆页面。
- 已保存作品再次使用该入口时，先保存最新修改。
- 如果存在版本一致的未完成会话，询问“继续上次进度”或“重新开始”。
- 如果未完成会话与最新作品结构版本不一致，不允许继续旧进度，只能取消或确认重新开始。
- 重新开始会把旧会话标记为 `abandoned`，再创建基于最新作品快照的新会话；不修改作品，不扣库存。

### 4.3 从“我的作品”进入

点击作品图片后打开统一底部操作弹窗，不直接进入编辑器。

弹窗顶部展示：

- 缩略图与作品名称。
- 图纸尺寸。
- 色号数量与总豆子数。
- 拼豆状态：未开始、进行中、已完成。
- 进行中时显示 `已完成色号 / 总色号`，例如 `4/8 色`。

操作项：

1. `开始拼豆`或`继续拼豆`。
2. `编辑作品`。
3. `分享作品`，复用现有社区分享能力。
4. `删除作品`，作为独立的红色危险操作。

删除确认文案需要说明：删除作品后未完成拼豆进度将无法继续，但不会回滚以前已经完成的库存出库记录。服务端将活动会话转为审计用的 `abandoned` 终态。

### 4.4 已有会话的入口规则

- 同一用户、同一作品最多有一个未完成会话。
- 所有入口先查询该会话。
- 存在会话时主操作文案为“继续拼豆”。
- 用户可以主动选择重新开始；旧活动会话标记为 `abandoned` 后再创建新会话。
- 已完成会话保留为完成记录，但不作为“继续拼豆”入口。

## 5. 库存检测设计

### 5.1 仓库选择

- 默认使用当前活动仓库。
- 有多个仓库时允许在检测结果顶部切换。
- 切换仓库后重新计算，不合并多个仓库库存。
- 没有仓库时提示创建仓库，也允许跳过检测直接开始。

### 5.2 检测计算

按色号计算：

`缺少数量 = max(图纸需要数量 - 当前仓库数量, 0)`

未录入库存的色号按 `0` 颗处理。

每行展示：

| 字段 | 示例 |
| --- | --- |
| 色号 | C4 |
| 色块 | 当前 MARD 221 颜色 |
| 图纸需要 | 61 颗 |
| 当前库存 | 56 颗 |
| 状态 | 缺 5 颗 |

汇总展示：

- 需要颜色数量。
- 总豆子数量。
- 库存充足色号数量。
- 库存不足色号数量。
- 总缺少数量。

### 5.3 检测结果状态

- 全部充足：绿色成功状态，主按钮“开始拼豆”。
- 部分不足：橙红提醒，列出缺豆色号，主按钮“仍然开始拼豆”。
- 检测失败：保留普通豆子清单，允许重试或跳过检测。
- 未登录：触发登录流程。
- 无仓库：显示“创建仓库”和“直接开始”两个操作。

### 5.4 检测结果不是库存锁定

检测结果只代表检测时刻的库存快照，不预占库存。开始页面的库存按钮必须能重新检测；最终扣减前必须再次由服务端校验。

## 6. “开始拼豆”页面

### 6.1 设计方向

页面采用参考图的五层结构：

1. 顶部状态栏。
2. 色号完成进度条。
3. 带坐标与辅助线的主画布。
4. 中间工具栏。
5. 底部色号轨道与完成按钮。

保持现有产品的蓝白色视觉系统；当前色使用橙色描边，库存异常使用橙红色，成功状态使用绿色。图标继续使用项目现有 Lucide/Icon 体系，不使用表情符号替代图标。

### 6.2 顶部状态栏

- 返回：打开中途退出确认。
- 库存：显示“库存充足”或“缺 2 色”，点击打开库存检测结果。
- 计时：显示累计时长，支持暂停和继续。
- 保存：立即保存当前会话进度。
- 设置：控制坐标尺、格子编号、辅助线和高亮强度。

### 6.3 色号进度条

- 进度定义为 `已完成色号数 / 总色号数`。
- 右侧显示 `4/8`，不使用容易误解的豆子颗数百分比。
- 已完成色号被取消完成后，进度同步回退。

### 6.4 图纸工作区

- 复用现有网格画布与手势能力。
- 支持双指缩放、拖动画布和一键适应。
- 显示横纵坐标尺。
- 每隔 5 格显示强化辅助线。
- 当前色号保持原色并可显示摆放序号。
- 其他未完成颜色统一压暗。
- 已完成色号显示更深遮罩和完成标记。
- “专注当前色”将当前色的边界区域适配到可视范围。

当前色序号默认按“从上到下，每行从左到右”生成。序号仅辅助摆放，不构成逐颗进度。

### 6.5 工具栏

- 搜色：搜索并切换作品中的色号。
- 标记：添加或移除临时位置标记；标记不影响完成进度。
- 高亮：开启或关闭当前色高亮。
- 锁定：锁定画布手势，防止误触移动。
- 更多：豆子清单、库存检测、重置当前色、显示设置。
- 适应：恢复完整画布视图。

### 6.6 底部色号轨道

每张色号卡展示：

- 色块。
- MARD 221 色号。
- 图纸需要数量。
- 完成状态。
- 缺货状态。

交互状态：

- 当前色：橙色外圈。
- 已完成：蓝色勾选。
- 库存不足：小型缺货标识，不禁用选择。
- 点击色号：切换当前色并自动保存。

排序方式：

- 默认图纸顺序。
- 数量从少到多。
- 数量从多到少。
- 色号顺序。
- 未完成优先。

### 6.7 完成当前色号

右侧固定主按钮显示 `完成 C4`。

点击后：

1. 标记当前色号完成。
2. 自动保存会话。
3. 更新进度。
4. 自动切换到下一个未完成色号。

取消已完成状态需要二次确认，防止误触。

## 7. 会话状态与保存

### 7.1 会话状态机

```text
未开始
  ↓ 创建会话
进行中 ↔ 已暂停
  ↓ 完成最后一个色号
待完成确认
  ├─ 完成并扣库存 → 已完成（已扣库存）
  ├─ 完成但不扣库存 → 已完成（未扣库存）
  └─ 返回检查 → 进行中

进行中
  ├─ 保存并退出 → 进行中（下次继续）
  └─ 放弃进度 → 已放弃
```

状态转换必须由服务端校验：

| 当前状态 | 允许操作 | 目标状态 |
| --- | --- | --- |
| 无会话 | 创建 | `in_progress` |
| `in_progress` | 暂停 | `paused` |
| `paused` | 继续 | `in_progress` |
| `in_progress/paused` | 保存普通进度 | 状态不变 |
| `in_progress/paused` | 完成最后一个色号 | `pending_completion` |
| `pending_completion` | 返回检查 | `in_progress` |
| `pending_completion` | 完成并扣库存 | `completed_deducted` |
| `pending_completion` | 完成但不扣库存 | `completed_without_deduction` |
| `in_progress/paused/pending_completion` | 放弃或重新开始 | `abandoned` |

`completed_deducted`、`completed_without_deduction` 和 `abandoned` 均为终态，拒绝普通进度更新和再次完成。完成最后一个色号必须调用显式状态转换接口，不能只由客户端修改完成色号数组。

进入 `pending_completion` 时自动结算并暂停计时。选择“返回检查”后保持暂停状态，由用户明确点击继续计时，避免完成确认停留时间被计入实际拼豆时长。

### 7.2 自动保存时机

- 完成或取消完成某个色号。
- 切换当前色号。
- 添加或删除临时标记。
- 暂停或继续计时。
- 手动点击保存。
- 点击退出。
- 页面进入后台或失去可见性。
- 定时兜底保存。

客户端可以先本地保存，再异步同步服务端。每次更新携带整数 `version`；服务端仅在版本匹配时更新并将版本加一。

首版冲突规则：

- 服务端版本优先，不自动合并两个设备的完成色号、标记或计时。
- 本机旧版本只能查看、放弃，或在用户明确确认后用“覆盖服务端进度”提交。
- 显式覆盖仅允许目标会话仍处于活动状态且作品快照一致；终态会话禁止覆盖。
- 离线时可以继续操作并写入当前账号隔离的本地草稿，但不能执行整件完成或库存扣减。
- 恢复网络后先同步；发生冲突时必须解决冲突后才能继续完成。

### 7.3 中途退出弹窗

- `保存进度并退出`。
- `继续拼豆`。
- `放弃本次进度并退出`。

保存退出和放弃进度都不扣库存。放弃进度需要二次确认。

### 7.4 图纸版本变化

会话绑定创建时的作品版本，并保存不可变的图纸快照。快照至少包含网格行列、每格 MARD 色号、每色需求数量、色号系统和作品显示名称。

如果编辑作品导致格子、尺寸、色号或数量变化：

- 旧活动会话标记为版本不匹配。
- 不自动迁移已完成色号。
- 再次进入时只能查看基于会话快照的旧进度、放弃旧进度，或确认重新开始；不能把旧进度继续写入新作品版本。
- 重新开始时将旧会话标记为 `abandoned`，再基于最新作品生成新快照。
- 版本不匹配后，除“查看、放弃旧会话、基于新版本重新开始”外，所有进度更新、暂停/继续、进入待完成和最终完成操作均被服务端拒绝。
- 旧版本会话绝对不能执行最终库存扣减，即使它已经在另一设备上打开。

仅修改作品名称不使会话失效。

## 8. 整件完成与库存扣减

### 8.1 完成弹窗

完成最后一个色号后提供：

1. `完成并扣减库存`。
2. `完成但不扣减库存`。
3. `返回检查`。

### 8.2 完成并扣减库存

服务端必须在一个数据库事务内完成：

1. 校验用户拥有作品、会话和仓库。
2. 以会话级比较并交换校验当前状态必须是 `pending_completion`。
3. 从会话的不可变需求快照读取每色数量，不从可变的当前作品或客户端请求读取。
4. 重新读取所有相关色号库存。
5. 校验每个色号库存均大于等于快照需要数量。
6. 按每个色号的快照需要数量出库。
7. 为每个色号写入库存流水，并关联会话 ID。
8. 将会话原子更新为 `completed_deducted`。

任一步失败都必须整体回滚。

同一个会话的完成请求必须满足两层保护：

- 请求幂等键用于安全重试；相同键返回首次结果。
- 会话终态用于阻止不同幂等键、不同设备或相反完成选择再次生效。

并发请求只有第一个从 `pending_completion` 成功转换终态的请求生效。后续请求返回当前终态和 `BEADING_ALREADY_COMPLETED`，不得再次扣库存或改写完成方式。

### 8.3 最终库存不足

如果完成时重新检测发现不足：

- 不进行任何部分扣减。
- 显示最新库存和缺少数量。
- 提供“返回处理库存”和“完成但不扣减”。
- 不允许形成负库存。

### 8.4 完成但不扣减库存

- 服务端以比较并交换把 `pending_completion` 原子更新为 `completed_without_deduction`。
- 保存完成时间、总用时和完成进度。
- 不修改仓库库存。
- 完成记录可从“我的作品”操作弹窗查看。
- 该选择是最终决定，之后不能通过同一会话补扣库存；如用户需要补记，必须使用仓库手动出库并形成独立流水。

### 8.5 删除作品与完成并发

删除作品和完成会话必须锁定或串行化同一项目与活动会话记录：

- 删除事务先成功：活动会话变为 `abandoned`，后续完成请求返回 `BEADING_INVALID_STATE`，不得扣库存。
- 完成事务先成功：完成状态与库存流水保留，随后允许删除作品；删除只把项目外键置空，不改写完成结果和流水。
- 两条路径都不能出现“会话显示已放弃但库存已扣减”的中间状态。

在 SQLite 中应使用覆盖整个校验和写入过程的写事务；迁移到支持行锁的数据库后锁定项目和会话行。

## 9. 建议数据模型

具体字段名可按现有数据库风格调整，但语义必须保留。

### 9.1 `beading_sessions`

- `id`
- `user_id`
- `project_id`，允许作品删除后置空
- `project_revision`
- `project_snapshot_json`：不可变的行列、每格色号和显示信息
- `requirements_json`：不可变的每色需求数量
- `status`：`in_progress | paused | pending_completion | completed_deducted | completed_without_deduction | abandoned`
- `warehouse_id`，可空
- `current_color_code`
- `completed_color_codes_json`
- `marks_json`
- `viewport_json`
- `elapsed_seconds`
- `timer_started_at`，可空
- `inventory_deducted`
- `inventory_deduction_idempotency_key`，可空
- `created_at`
- `updated_at`
- `completed_at`，可空
- `version`：乐观并发控制整数

约束：同一用户、同一作品最多存在一个 `in_progress/paused/pending_completion` 会话。数据库必须使用活动会话部分唯一索引，或在不支持部分索引时使用等效的事务锁定/唯一活动键，不能只依赖前端先查询后创建。

### 9.2 作品版本

保存作品时生成稳定的结构版本：

- 推荐使用网格尺寸、每格色号和调色系统形成内容摘要。
- 名称、缩略图或分享状态变化不改变结构版本。
- 创建会话时若没有任何有效豆子色号，返回 `BEADING_PROGRESS_INVALID`，不创建空会话。
- 快照中出现不属于当前色号系统的非法色号时拒绝创建，不静默映射。
- 同一色号的需求项必须合并求和并按色号保存为唯一项；最终扣减只读取规范化后的唯一需求列表。

### 9.3 库存流水扩展

库存流水需要可选关联：

- `beading_session_id`
- `project_id`
- `source`，值为 `manual` 或 `beading_completion`
- `project_name_snapshot`
- `color_code`
- `quantity`

用于审计和防止重复扣减。

作品删除策略：

- 删除作品时把活动会话标记为 `abandoned`。
- 会话和库存流水中的 `project_id` 使用 `ON DELETE SET NULL` 或等效逻辑。
- 已完成和已放弃会话保留不可变快照作为审计数据，但不再出现在“我的作品”列表。
- 库存流水保留会话 ID、作品名称快照、色号和数量，不因作品删除而删除。

## 10. 建议接口边界

接口路径遵循现有 `/api/v1` 风格，最终名称可按项目路由规范微调。

所有会话响应至少返回：`id`、`status`、`version`、`projectRevision`、`revisionMatched`、`readOnlyReason?`、`currentColorCode`、`completedColorCodes`、`elapsedSeconds`、`warehouseId`、`updatedAt`。所有写请求返回更新后的完整会话摘要。

除查询、库存查看和放弃操作外，每个会话写接口都必须在服务端重新比较当前项目结构版本与 `projectRevision`。不一致时返回 `409 BEADING_PROJECT_REVISION_MISMATCH`，并把会话作为只读旧版本返回。

项目结构版本校验、会话版本 CAS 和会话写入必须处于同一个事务或锁定范围内，不能先在事务外校验再写入。

### 10.1 库存检测

- `POST /projects/:projectId/inventory-check`：尚未创建会话时按当前保存作品检测。
- `POST /beading-sessions/:sessionId/inventory-check`：已有会话时按不可变会话需求快照检测。

输入：`warehouseId`。  
输出：`projectRevision`、`warehouseId`、`items[{ code, required, available, missing }]` 和汇总。

库存检测以服务端保存的作品内容或会话快照为准，不能信任客户端上传的需求数量。拼豆页面和最终完成前必须使用会话级检测。

### 10.2 查询或创建会话

- `GET /projects/:projectId/beading-session`
- `POST /projects/:projectId/beading-session`

创建输入：`warehouseId?`、`restart?: boolean`、`expectedProjectRevision`。创建时由服务端读取最新作品结构并生成不可变快照，不接受客户端上传快照或需求数量。

- 已有版本一致的活动会话且未要求重启：返回该会话，`created: false`。
- `restart: true`：在同一事务中把旧活动会话标记为 `abandoned`，再创建新会话。
- 当前项目版本与 `expectedProjectRevision` 不一致：返回 `409 BEADING_PROJECT_REVISION_MISMATCH`，客户端重新检测库存后再创建。
- 已有版本不一致会话且未要求重启：返回 `409 BEADING_PROJECT_REVISION_MISMATCH`。
- 并发创建依赖数据库唯一约束；冲突后读取并返回已成功创建的活动会话。

### 10.3 保存会话进度

`PATCH /beading-sessions/:sessionId`

允许更新：

- 当前色号。
- 已完成色号。
- 临时标记。
- 视口状态。
- 计时状态。
- 仓库选择。

请求必须携带 `version`。仅 `in_progress/paused` 允许普通进度更新；版本不匹配返回 `409 BEADING_VERSION_CONFLICT` 和服务端当前会话。

显式覆盖不绕过并发检查。用户查看冲突时的服务端版本并确认覆盖后，客户端提交 `overwriteExpectedServerVersion`；服务端仍以该版本执行 CAS。确认后服务端若再次更新，覆盖请求继续返回版本冲突，用户必须重新查看并确认。显式覆盖也不能绕过作品结构版本检查或终态限制。

### 10.4 会话状态转换

- `POST /beading-sessions/:sessionId/pause`
- `POST /beading-sessions/:sessionId/resume`
- `POST /beading-sessions/:sessionId/prepare-completion`
- `POST /beading-sessions/:sessionId/return-to-progress`

均要求 `version`，并重新校验当前项目结构版本。`prepare-completion` 由服务端验证快照中的所有色号都已完成，并原子转为 `pending_completion`。

### 10.5 放弃会话

`POST /beading-sessions/:sessionId/abandon`

输入：`version`、`reason: user_abandon | restart | project_deleted | revision_mismatch`。不扣库存。放弃是版本不匹配时唯一允许的写操作；终态重复调用返回当前结果。

### 10.6 完成会话

`POST /beading-sessions/:sessionId/complete`

输入：

- `deductInventory: boolean`
- `warehouseId`，扣库存时必填；可以不同于会话此前选择的仓库
- `idempotencyKey`
- `version`

输出：会话完成状态、库存扣减结果和更新后的库存摘要。

仅 `pending_completion` 可以完成。不同完成请求并发时，第一个成功的状态转换决定最终结果；其余请求返回 `409 BEADING_ALREADY_COMPLETED` 和当前终态。

完成接口必须重新校验当前项目结构版本。选择扣库存时，以请求中的仓库作为本次实际扣减仓库；事务成功后同时把该仓库写入会话的 `warehouse_id`，并让会话、库存流水和完成响应保持一致。仓库不存在、无权限或色号系统不兼容时整体失败。

幂等键作用域为“用户 + 会话”。服务端保存请求指纹，至少包含 `deductInventory`、`warehouseId` 和会话版本；同一幂等键携带不同指纹时返回 `409 BEADING_IDEMPOTENCY_CONFLICT`。

幂等记录需要独立保存幂等键、请求指纹和首次响应摘要；相同请求重试直接重放首次结果，便于库存审计和网络超时恢复。

### 10.7 关键错误码

| HTTP | 错误码 | 含义 |
| --- | --- | --- |
| 400 | `BEADING_PROGRESS_INVALID` | 完成色号不属于快照或尚未完成全部色号 |
| 401 | `AUTH_REQUIRED` | 未登录或令牌失效 |
| 403 | `BEADING_FORBIDDEN` | 不拥有项目、会话或仓库 |
| 404 | `BEADING_SESSION_NOT_FOUND` | 会话不存在 |
| 409 | `BEADING_ACTIVE_SESSION_EXISTS` | 并发创建命中活动会话约束 |
| 409 | `BEADING_VERSION_CONFLICT` | 会话版本冲突 |
| 409 | `BEADING_PROJECT_REVISION_MISMATCH` | 项目结构版本与活动会话不一致 |
| 409 | `BEADING_ALREADY_COMPLETED` | 会话已由其他请求完成 |
| 409 | `BEADING_INVALID_STATE` | 当前状态不允许该操作 |
| 409 | `BEADING_IDEMPOTENCY_CONFLICT` | 相同幂等键对应了不同完成参数 |
| 409 | `BEADING_INVENTORY_INSUFFICIENT` | 最终库存不足，未执行任何扣减 |
| 422 | `BEADING_COLOR_SYSTEM_UNSUPPORTED` | 图纸无法映射到受支持的库存色号系统 |

## 11. 前端模块边界

建议拆分为独立职责模块，避免继续扩大 `H5App.tsx`：

- `InventoryCheckSheet`：库存检测与缺豆结果。
- `BeadingSessionPage`：开始拼豆页面壳层。
- `BeadingCanvas`：高亮、坐标、辅助线和手势。
- `BeadingToolbar`：搜色、标记、高亮、锁定、更多、适应。
- `BeadingColorRail`：色号切换、排序和完成状态。
- `BeadingExitDialog`：退出与放弃。
- `BeadingCompletionDialog`：完成和库存扣减选择。
- `ProjectActionSheet`：我的作品操作弹窗。
- 会话 API 客户端与纯状态计算工具单独放置。

豆子清单继续复用现有 `BeadListDrawer`，通过可选操作区接入库存检测和开始拼豆，不为不同页面复制新的豆子清单。

## 12. 异常与边界状态

### 12.1 网络异常

- 自动保存失败时保留本地草稿并显示“等待同步”。
- 离线时允许切换色号、完成色号、标记和计时；禁止执行整件完成和库存扣减。
- 恢复网络后先用草稿基于的 `version` 重试同步。
- 用户退出前仍保存本地草稿。
- 库存扣减失败不得在客户端显示为已扣减。

### 12.2 多设备冲突

- 会话更新使用乐观版本控制。
- 发现服务端版本更新时提示“另一设备已有新进度”。
- 首版不自动合并完成色号。
- 用户可以加载服务端进度并丢弃本机草稿，或查看本机草稿后明确选择覆盖。
- 覆盖只允许服务端会话仍为活动状态、作品快照一致；终态或版本不匹配时只能采用服务端结果。

### 12.3 作品或仓库被删除

- 作品删除：活动会话转为 `abandoned`；项目外键置空；已完成、已放弃会话和库存审计流水保留快照但不在作品列表展示。
- 仓库删除：会话保留，但清空仓库关联；完成时可以重新选择仓库。
- 色号系统不一致：库存检测不可用，但仍允许无库存模式开始。

### 12.4 页面刷新或浏览器回收

- 从本地缓存快速恢复界面。
- 登录后再与服务端会话同步。
- 计时使用累计秒数加时间戳计算，不依赖持续运行的前端定时器。
- 本地缓存键必须包含用户 ID 和会话 ID，不能只使用项目 ID。
- 退出登录时清除该用户所有未同步拼豆草稿；若存在未同步进度，退出确认中明确提示。
- 删除作品、放弃会话或收到终态响应后，清除对应本地草稿。
- 登录为另一个账号时绝不加载前一个账号的本地草稿。

## 13. 可用性与视觉要求

- 核心触控区域不小于 44px。
- 底部色号轨道可横向滚动，主完成按钮固定可见。
- 页面考虑 iOS 安全区和浏览器底部栏。
- 当前色不能只依赖颜色区分，必须同时有描边和文本状态。
- 库存不足不能只用红色，必须显示“缺 N 颗”。
- 按钮和弹窗沿用项目统一底部弹窗规范。
- 尊重 `prefers-reduced-motion`。
- 计时暂停、保存成功、同步失败需要文本状态反馈。

## 14. 测试要求

### 14.1 纯逻辑测试

- 按图纸统计每个 MARD 色号用量。
- 库存充足、部分不足、全部缺失的差值计算。
- 色号完成、取消完成和进度计算。
- 当前色自动切换到下一个未完成色号。
- 作品版本摘要稳定性。
- 会话状态机合法转换。

### 14.2 API 集成测试

- 用户只能读取和修改自己的作品、会话和仓库。
- 同一作品只创建一个未完成会话。
- 两个并发创建请求最终只产生一个活动会话。
- 进度更新的版本冲突。
- 终态会话拒绝普通进度更新。
- 完成最后一个色号通过状态转换进入 `pending_completion`。
- 完成但不扣库存。
- 库存充足时按每色实际数量原子扣减。
- 任一色号不足时全部回滚。
- 相同幂等键重复请求不会二次扣减。
- 不同幂等键并发完成只有一个结果生效。
- “不扣减”完成后不能再通过同一会话补扣。
- 会话需求快照不受后续项目编辑影响。
- 项目版本变化后，所有普通更新和最终完成均被拒绝，只有查看、放弃和重新开始可用。
- 项目级库存检测后作品发生变化时，携带旧 `expectedProjectRevision` 创建会话会失败。
- 删除作品与完成扣减并发时，只有一个事务路径生效且库存与会话终态一致。
- 最终选择的新仓库会同时写入会话、流水和响应。
- 相同幂等键使用不同完成参数返回冲突。
- 零有效色号、快照非法色号和重复色号被拒绝或规范化为唯一需求项。
- 检测后仓库被删除时，最终完成整体失败且不扣库存。
- 删除作品清理未完成会话，但不删除历史库存流水。

### 14.3 前端交互测试

- 保存并开始拼豆必须等待保存成功。
- 我的作品图片点击打开操作弹窗。
- 未开始显示“开始拼豆”，进行中显示“继续拼豆”。
- 库存不足仍可进入拼豆页。
- 完成色号后更新勾选、进度并切换下一色。
- 中途退出保存后可以恢复。
- 完成弹窗三个分支均符合规则。
- 图纸版本变化时不错误复用旧进度。
- 离线时不能执行整件完成或库存扣减。
- 多设备冲突不自动合并，用户选择服务端版本或显式覆盖。
- 登出、切换账号、删除作品和放弃会话会正确清理身份隔离的本地草稿。

### 14.4 手工验收设备

- iPhone Safari，包含 HTTP 临时兼容环境。
- Android Chrome。
- 320px、375px、390px 和 414px 宽度。
- 大图纸与 104×104 图纸的缩放、拖动和高亮性能。

## 15. 验收标准

1. 用户能从豆子清单检测指定仓库库存，并看到每色缺少数量。
2. 库存不足时可以明确选择“仍然开始拼豆”。
3. 编辑器保存弹窗有“保存并开始拼豆”，且保存失败不进入拼豆页。
4. 我的作品点击图片会打开操作弹窗，并包含开始/继续拼豆、编辑、分享和删除。
5. 开始拼豆页面布局接近参考图，主画布、工具栏、色号轨道和完成按钮层级清晰。
6. 完成进度以色号为单位，完成当前色后自动切换下一色。
7. 中途退出能恢复当前色、完成色号、计时和标记，且不扣库存。
8. 完成整件作品时可以选择是否扣减库存。
9. 库存扣减为一次性原子操作，失败不产生部分扣减，重复请求不重复扣减。
10. 图纸结构发生变化后不会静默套用旧拼豆进度。
11. 所有新增底部弹窗遵循现有统一弹窗规范。
12. 会话使用不可变图纸与需求快照，多设备并发完成只能产生一个最终结果。
13. 本地草稿按用户隔离，离线时不能最终完成或扣减库存。
14. H5 构建、现有测试和新增测试全部通过。

## 16. 建议实施顺序

Codex Goal 应按以下顺序实施并在每阶段验证：

1. 提取图纸色号需求计算与库存检测纯函数。
2. 增加服务端库存检测接口和测试。
3. 增加拼豆会话数据模型、迁移、接口和状态机测试。
4. 实现原子且幂等的最终库存扣减。
5. 扩展豆子清单操作区和库存检测弹窗。
6. 实现“我的作品”操作弹窗。
7. 扩展保存弹窗，加入“保存并开始拼豆”。
8. 实现开始拼豆页面、色号进度和会话自动保存。
9. 实现退出、恢复、完成确认和版本不匹配处理。
10. 完成响应式、可访问性、性能和全量回归验证。
